Step 0 · Big picture

Two labs in one: fake AWS + fake Kubernetes

Lab 1 is practice on fake infrastructure that behaves exactly like the real thing — so you can safely press every button and break nothing.

The two halves of Lab 1
🔑 Session A — Identity on AWS Uses LocalStack (a fake AWS that runs in Docker). Practice: who can log in, and what they may do.
  • 👤 Users — people logins
  • 👥 Groups — teams with permissions
  • 📜 Policies — the permission list
  • 🔐 Access keys — passwords for programs
➜
🛡️ Session B — Access on Kubernetes Uses kind (a tiny Kubernetes cluster in Docker). Practice: the same idea, but with roles instead of policies.
  • 🏠 Namespaces — separate rooms
  • 🤖 ServiceAccounts — robot identities
  • 📋 Roles — job descriptions
  • 🔗 RoleBindings — hiring contracts

Same philosophy in both: identity + permission + proof. You create an identity, give it exactly the permissions it needs, then run checks to prove the walls hold.

Session A · Getting the fake AWS running

Setup — wake up LocalStack

Before any IAM work, we start a container that pretends to be AWS. The AWS command-line tool happily talks to it — the only difference is we add a flag that says "talk to the fake one, not the real cloud".

1Start the fake AWS (LocalStack)

CommandWhat it does, in easy words
docker --versionChecks Docker is installed before we try anything.
docker run -d --name localstack
-p 4566:4566 localstack/localstack		Starts the fake-AWS container. -d = run in background; --name = give it a nickname; -p 4566:4566 = let your computer talk to it on port 4566.
curl http://localhost:4566/_localstack/healthAsks LocalStack "are you awake?" — it lists which fake AWS services are running.

2Give the AWS tool dummy login info

CommandWhat it does, in easy words
aws configure set aws_access_key_id test (×3)Stores dummy login info (test/test, region us-east-1). The AWS tool refuses to work without some credentials — and LocalStack accepts anything.
aws --endpoint-url=http://localhost:4566
sts get-caller-identity		"Who am I right now?" — confirms the tool is talking to LocalStack (account 000000000000), not real AWS.
EP='--endpoint-url=http://localhost:4566'Creates a shortcut. EP stands for "talk to LocalStack". Every later command just types $EP instead of the long URL.
Why this matters: the real AWS is dangerous (and costs money). Pointing the same tool at LocalStack means every command you run is 100% safe practice.
The cast of Session A

IAM in one picture: who has what

Everything in Session A is about the same shape: permissions are written down once (a policy), and people get them by being added to a group or having a policy attached directly.

Permissions flow: groups & policies
👑 Root account All-powerful. Rule of thumb: never use it for daily work.
⇩
👥 Group: Admins A team. The permission lives here, not on any one person.
  • 📜 AdministratorAccess policy attached → "do everything"
  • 👤 Member: CloudAdmin_Lisa — inherits the group's powers automatically
👤 User: Analyst_Raisha A teammate with a different job. Least privilege: only what her job needs.
  • 📜 AmazonS3ReadOnlyAccess attached directly → "look but don't touch"
  • 🔐 Access key → lets a program log in as her
Why groups? Manage permissions in one place. Members come and go by joining / leaving the team — the permission list never changes.
Why least privilege? Raisha can read S3 files but can't delete or write them. If her account is stolen, the damage is limited to reading.
Session A · Task 2

Create an admin that isn't "root"

Instead of using the all-powerful root account, we make a team with full power and put a real person in it.

2The commands

CommandWhat it does
aws $EP iam create-group
--group-name Admins		Makes an empty team called Admins.
aws $EP iam attach-group-policy
--policy-arn ...AdministratorAccess		Gives the whole team the "do everything" permission (AdministratorAccess) instead of giving it to one person.
aws $EP iam list-attached-group-policies
--group-name Admins		Asks "what permissions does the Admins team have?" — proof the policy is attached.
aws $EP iam create-user
--user-name CloudAdmin_Lisa		Creates a personal login (CloudAdmin_Lisa) so you stop using the all-powerful root account.
aws $EP iam add-user-to-group
--group-name Admins --user-name CloudAdmin_Lisa		Puts Lisa into the Admins team. Now she inherits the team's powers automatically.
aws $EP iam get-group
--group-name Admins		"Who's in the Admins team?" — proof Lisa is a member.
Why groups: you manage permissions in one place (the team), and members come and go by joining/leaving. Nobody gets personal "superpowers" attached to their account.
Session A · Task 3

A read-only teammate

Raisha's job is analysis: she needs to look at S3 files, never change or delete them. So she gets exactly that — nothing more.

3The commands

CommandWhat it does
aws $EP iam create-user
--user-name Analyst_Raisha		Creates a second login for a teammate.
aws $EP iam attach-user-policy
--user-name Analyst_Raisha
--policy-arn ...AmazonS3ReadOnlyAccess		Gives Raisha only "look but don't touch" permission on S3 files (least privilege).
aws $EP iam list-attached-user-policies
--user-name Analyst_Raisha		Shows the single read-only policy attached to her — proof she can't delete or write.
Spot the difference from Task 2: Lisa got power through a group; Raisha got a policy attached directly to her. Both work — the group way scales better as a company grows.
Session A · Task 4

Access keys — passwords for programs

People log in with a username + password. Programs log in with a key pair: an ID plus a secret. Keys can be switched off at any time — that's the kill-switch.

4The commands

CommandWhat it does
aws $EP iam create-access-key
--user-name Analyst_Raisha		Generates a secret "program key" (ID + secret) so a script can log in as Raisha without a console password.
aws $EP iam list-access-keys
--user-name Analyst_Raisha		Lists her keys and their status (Active / Inactive).
aws $EP iam update-access-key
--user-name Analyst_Raisha
--access-key-id <ID> --status Inactive		Switches one key off — that's rotation: if a key leaks, you turn it off and make a new one.
Mental model: think of an access key like a hotel key card. Lost it? Deactivate the old card (--status Inactive), issue a new one, done. The old card is worthless.
Session B · Kubernetes access control

Same idea, inside a tiny cluster

Kubernetes splits "what you may do" (Role) from "who gets to do it" (RoleBinding). A role does nothing until it's bound to an identity.

RBAC flow — dev namespace
🤖 ServiceAccount devsofia — a "robot identity" representing a developer, created inside the dev room.
➜
🔗 RoleBinding dev-user-binding — the hiring contract: "this identity has this job, in this room."
➜
📋 Role pod-reader — the job description: in dev, may only get / list / watch pods.
🚫 prod namespace No binding for devsofia here. The job description only exists in the dev room — so in prod, she can do nothing.
✅ The proof: kubectl auth can-i "Can this identity do this?" — answered without actually doing it. It's the lab's way of testing the walls you just built.
  • yes list pods in dev — the role allows it
  • no delete pods in dev — delete isn't in the role's verbs
  • no list pods in prod — the binding only covers dev

BThe commands

CommandWhat it does
kind create cluster
--name ccse-lab1		Creates a small, disposable Kubernetes cluster in Docker (free practice cluster).
kubectl cluster-info
--context kind-ccse-lab1		"Is the cluster's brain reachable?"
kubectl get nodesLists the cluster's computers (nodes) — should show Ready.
kubectl create namespace dev
kubectl create namespace prod		Makes two separate rooms (dev, prod) inside the cluster.
kubectl get namespacesLists all rooms — proof both exist.
kubectl create serviceaccount devsofia
-n dev		Creates a "robot identity" called devsofia that represents a developer, inside the dev room.
kubectl create role pod-reader -n dev
--verb=get,list,watch --resource=pods		Writes a job description (role): in the dev room you may only look at pods (get/list/watch) — nothing else.
kubectl create rolebinding dev-user-binding -n dev
--role=pod-reader
--serviceaccount=dev:devsofia		Hires devsofia for that job: "this identity has the pod-reader job in the dev room". A role does nothing until it's bound to someone.
kubectl auth can-i list pods -n dev
--as=$SA		"Can this identity list pods?" — answers yes/no without actually doing it. The --as= says "pretend you're this identity".
kubectl auth can-i delete pods -n dev
--as=$SA		Same check but for deleting — answers no (not in the job description).
kubectl auth can-i list pods -n prod
--as=$SA		Same check in the other room — answers no, because the job is only in dev.
kubectl get rolebinding dev-user-binding
-n dev -o yaml		Prints the hiring contract as YAML — evidence that the binding is exactly as configured.
Why RBAC exists: real clusters are shared. One team's mistake shouldn't be able to delete another team's data — so every identity gets a narrow job description, and rooms (namespaces) keep things apart.

Cheat sheet

The flags you'll see everywhere

Half of "understanding the command" is understanding the little flags. Here's every one used in Lab 1.

-drun in the background (container keeps running, terminal is free)
--namegive the container a nickname to reference later
-p 4566:4566port mapping — "let my computer talk to the container on port 4566"
--endpoint-url"talk to LocalStack at this address, not real AWS"
$EPthe shortcut variable standing in for --endpoint-url=...
-nnamespace — which Kubernetes room the command applies to
--as=impersonate — "pretend you are this identity" for a can-i check
--verb=the actions a role allows: get, list, watch, create, delete…
--resource=the thing the role covers: pods, secrets, deployments…
-o yamloutput format — print the full YAML definition as evidence
When you're done

Cleanup — leave no trace

CommandWhat it does
kind delete cluster
--name ccse-lab1		Destroys the practice cluster.
docker stop localstack &&
docker rm localstack		Stops and removes the fake AWS container.
Why clean up? These are disposable practice environments. Deleting them is itself good cloud hygiene — and keeps Docker from eating your disk.
The whole lab in three lines

One-line takeaway

🔑 Session A = IAM

Who can log in and what they may do — users, groups, policies, and access keys. Groups carry permissions; people join groups.

🛡️ Session B = RBAC

The same idea in Kubernetes. A Role says what, a RoleBinding says who gets it, and namespaces keep rooms apart.

✅ The test that proves it

kubectl auth can-i answers "may this identity do this thing?" — the walls either hold (no) or don't (yes). Least privilege = the goal; the test = the proof.
