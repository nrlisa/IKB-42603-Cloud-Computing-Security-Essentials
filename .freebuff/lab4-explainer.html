The cast of Lab 3

Architecture — who protects what

Data protection covers three dimensions: at rest (on disk), in transit (on the wire), and integrity (has anyone changed it?).

Data Protection Architecture (Lab 3)
📦 Data at Rest Data sitting on disk is encrypted so stealing the file is useless.
  • 🔒 AES-256 — fast symmetric encryption (Task 1)
  • 🔓 RSA-2048 — asymmetric + digital signatures (Task 2)
🌐 Data in Transit Data moving across the network is encrypted so eavesdroppers see gibberish.
  • 🔒 TLS / HTTPS — nginx serves the record over port 8443 (Task 3)
  • Self-signed cert proves the concept (real certs use a CA)
🔍 Integrity Proof that nobody has changed the data.
  • 📋 SHA-256 hash — fingerprint of the file (Task 7)
  • 🔗 Hash chain — each log entry includes the previous hash
🔑 LocalStack KMS — The brain behind the keys Manages master keys, implements envelope encryption, and makes deletion provable (Tasks 4–6).
  • CMK (Customer Master Key) wraps data keys
  • Per-tenant isolation: one tenant's key can't decrypt another's data
  • Cryptographic erasure: destroy the key → data is permanently unrecoverable
Session A · Task 1

Symmetric Encryption — AES-256 (Data at Rest)

One shared key does both encryption and decryption. Fast and strong — but how do you share the key securely?

1The commands

CommandWhat it does
openssl enc -aes-256-cbc -pbkdf2 -salt -in record.txt -out record.encEncrypts the file with AES-256. -pbkdf2 = strong key derivation from a passphrase; -salt = random value to prevent rainbow-table attacks. You'll be prompted for a passphrase (the key).
cat record.encProves the encrypted file is unreadable ciphertext — not the original patient record.
openssl enc -d -aes-256-cbc -pbkdf2 -in record.enc -out record.dec.txtDecrypts back to plaintext. -d = decrypt mode.
diff record.txt record.dec.txt && echo 'MATCH: decryption successful'Proves the round-trip worked — the decrypted file is identical to the original.
Why this matters: AES-256-CBC is the industry standard for encrypting data at rest. One key does both jobs — fast, but if that key leaks, everything is exposed.

QIn your report: What is the key-distribution problem?

What is the key-distribution problem with symmetric encryption, and why does it matter for the cloud?

Answer: Both sender and receiver must possess the same secret key before any encrypted communication can occur, and that key must be transmitted through a separate, secure channel. If intercepted, an attacker can decrypt all past and future messages.

This matters for the cloud because:
  • Scale: Thousands of instances, services and tenants each need keys — pairwise sharing is unmanageable.
  • No physical security: Cloud storage is virtualized and multi-tenant — no trusted courier to deliver keys.
  • Key lifecycle: Rotation, revocation and destruction are hard when every party holds a copy.
  • Compliance: PDPA, PCI-DSS require centralised key control — manual distribution violates audit requirements.

This is why cloud platforms use a KMS — it keeps the master key in a hardware-protected module and lets services request encryption/decryption through API calls instead of sharing raw keys.

Session A · Task 2

Asymmetric Encryption & Digital Signatures — RSA-2048

Two keys, two jobs: the public key encrypts (anyone can lock), the private key decrypts (only you can unlock). Signatures flip the roles — private signs, public verifies.

2The commands

CommandWhat it does
openssl genrsa -out private.pem 2048Generates a 2048-bit RSA private key. This is your secret — never share it.
openssl rsa -in private.pem -pubout -out public.pemExtracts the public key from the private key. This one can be shared freely.
openssl pkeyutl -encrypt -pubin -inkey public.pem -in record.txt -out record.rsaEncrypts with the public key — anyone can do this.
openssl pkeyutl -decrypt -inkey private.pem -in record.rsa -out record.rsa.txtDecrypts with the private key — only the owner can do this.
openssl dgst -sha256 -sign private.pem -out record.sig record.txtSigns the file with the private key — proves who created it.
openssl dgst -sha256 -verify public.pem -signature record.sig record.txtVerifies the signature with the public key — output: Verified OK.
Notice the role reversal: encryption uses public, signing uses private. This is the basis of PKI and TLS — the same two-key system that protects HTTPS connections worldwide.
Session A · Task 3

Encryption in Transit — TLS / HTTPS

Over plain HTTP, anyone on the network can read the record. TLS wraps the connection in encryption so eavesdroppers see gibberish.

3The commands

CommandWhat it does
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 7 -nodes -subj '/CN=localhost'Creates a self-signed certificate for localhost. -x509 = certificate format; -days 7 = expires in a week; -nodes = no passphrase on the key.
docker run --rm -d --name tls -p 8443:443 -v $(pwd)/cert.pem:/etc/nginx/cert.pem -v $(pwd)/key.pem:/etc/nginx/key.pem -v $(pwd)/record.txt:/usr/share/nginx/html/record.txt nginxStarts nginx in a container, serving the record over HTTPS on port 8443.
curl -k https://localhost:8443/record.txtConnects over TLS and fetches the record. -k = accept the self-signed certificate (in production, a CA would sign it).
Compare with plain HTTP: over HTTP the record would travel in cleartext and any on-path attacker could read it (eavesdropping). TLS makes intercepted traffic unreadable.

End of Session A. Stop the TLS container: docker stop tls. Keep the ciphertext, keys, and outputs for the report.

Session B · Key Management at Scale

Same idea, cloud-style

Real cloud environments don't encrypt with a local passphrase. A Key Management Service (KMS) holds master keys in hardware, generates data keys on demand, and makes deletion provable.

How KMS solves the key-distribution problem
🔑 CMK (Master Key) Lives inside KMS, never leaves the hardware module. Small, protected, rotates infrequently.
⇩ wraps
📦 DEK (Data Key) Random one-time key. Encrypts the actual data locally. Used once, then discarded.
⇩ protects
📄 Encrypted Data The actual patient record, encrypted with the DEK. The DEK is stored wrapped by the CMK alongside it.

This is envelope encryption: the master key is too slow for bulk data, and the data key is too short-lived to need heavy protection. Together they give you both performance and security.

Session B · Task 4

Create and Use a KMS Master Key

Instead of typing a passphrase locally (like Task 1), we ask the KMS to create a master key that never leaves its hardware boundary.

4The commands

CommandWhat it does
EP='--endpoint-url=http://localhost:4566'Creates a shortcut. Every later command types $EP instead of the long LocalStack URL.
aws $EP kms create-key --description 'CCSE tenant-A master key'Asks KMS to create a Customer Master Key. Captures the KeyId for later use.
KEY_A=<PASTE_KEYID>Saves the key ID so subsequent commands know which key to use.
aws $EP kms encrypt --key-id $KEY_A --plaintext "$(echo -n 'hello' | base64)" --query CiphertextBlob --output textEncrypts a small secret directly with the master key — proves the key works. Returns a base64 ciphertext blob.
Why this matters: the master key is the cloud analogue of the passphrase from Task 1, but it never leaves the KMS. Encryption and decryption happen through API calls — no raw key is ever on disk.
Session B · Task 5

Envelope Encryption

For large data, you don't encrypt with the master key directly. You generate a one-time data key, encrypt locally with it, then wrap the data key with the master key.

5The commands

CommandWhat it does
aws $EP kms generate-data-key --key-id $KEY_A --key-spec AES_256 --query '[Plaintext,CiphertextBlob]' --output textAsks KMS for a data key. Returns two things: the plaintext key (for local encryption) and the wrapped copy (encrypted by the master key). Save them as datakey.b64 and datakey.enc.
base64 -d datakey.b64 > datakey.binDecodes the plaintext data key from base64 to raw binary.
openssl enc -aes-256-cbc -pbkdf2 -in record.txt -out record.env.enc -pass file:./datakey.binEncrypts the record locally using the data key — fast, because AES is fast and the file could be huge.
rm datakey.bin datakey.b64Destroys the plaintext data key from disk — only the KMS-wrapped copy (datakey.enc) survives. This is the critical step.
Why envelope encryption: the master key is small and slow — good for wrapping, bad for bulk data. The data key is fast and one-time — good for bulk data, but short-lived enough that it doesn't need heavy protection.
Session B · Task 6

Per-Tenant Keys & Cryptographic Erasure

Each tenant gets their own master key. Deleting a tenant's key makes their data permanently unrecoverable — provable deletion, even in the cloud.

6The commands

CommandWhat it does
aws $EP kms create-key --description 'CCSE tenant-B master key'Creates a second master key for tenant B — proves one tenant's key can't decrypt another's data.
aws $EP kms schedule-key-deletion --key-id $KEY_A --pending-window-in-days 7Schedules tenant A's key for permanent deletion (minimum 7-day waiting period).
aws $EP kms disable-key --key-id $KEY_ADisables the key immediately — even before the deletion window, it can't be used.
aws $EP kms decrypt --ciphertext-blob fileb://datakey.enc 2>&1 | head -3Attempts to unwrap tenant A's data key — it fails. The key is gone, so the encrypted record is permanently unrecoverable.
Critical point: Once the master key is gone, record.env.enc is just noise — no one, not even the cloud provider, can decrypt it. This is cryptographic erasure: deletion is provable because the key no longer exists.
Session B · Task 7

Integrity & Tamper-Evidence

Encryption protects confidentiality; hashing protects integrity. A hash chain makes a log tamper-evident — any modification is immediately detectable.

7The commands

CommandWhat it does
sha256sum record.txtComputes the SHA-256 fingerprint of the file — a unique, fixed-length hash.
cp record.txt tampered.txt; echo 'x' >> tampered.txtCreates a tampered copy by appending one character.
sha256sum record.txt tampered.txtProves the two hashes differ — even a one-character change produces a completely different hash.
PREV=0
for line in 'login ok' 'file read' 'export data'; do
PREV=$(echo -n "$PREV$line" | sha256sum | cut -d' ' -f1)
echo "$line | $PREV"
done		Builds a hash chain: each log entry includes the hash of the previous entry. Modifying an earlier entry breaks every subsequent link.
Why hash chains: in a plain log, an attacker can modify an old entry without detection. In a hash chain, every entry is cryptographically bound to the one before it — tampering is immediately detected by recomputing.

Lab 3 — Security Concepts Quiz
🔑 The key-distribution problem. Both parties need the same secret key, but sharing it securely is hard — especially at cloud scale. If the key leaks during transmission, everything encrypted with it is exposed. This is why we move to asymmetric encryption (Task 2) or a KMS (Session B).
🔓 Public key encrypts, private key decrypts. Anyone with the public key can lock data; only the private key owner can unlock it. Signatures flip the roles: private signs, public verifies. This two-key system is the basis of PKI and TLS.
📦 Envelope encryption. The master key is slow (hardware-protected) and expensive to use for bulk data. Instead, generate a fast one-time data key, encrypt locally with it, and wrap the data key with the master key. The master key only ever encrypts small data keys — never the actual data.
💀 Cryptographic erasure. In the cloud, storage is replicated and shared — you can't reliably overwrite every copy. But if you destroy the key that encrypted the data, every copy (including backups) becomes unreadable. Deletion is provable because the key no longer exists.
🔗 Each entry includes the hash of the previous entry. Modifying an earlier entry changes its hash, which breaks every subsequent link in the chain. An auditor can recompute all hashes from the beginning — any mismatch proves tampering occurred.
🌐 -k skips certificate verification. In the lab, we use a self-signed certificate, so curl would reject it without -k. In production, -k is dangerous because it accepts any certificate — including one from a man-in-the-middle attacker. Always use proper CA-signed certificates.

Key Takeaway

🔐 Session A = Crypto by Hand

AES-256 encrypts data at rest, RSA-2048 proves identity and integrity, and TLS protects data in transit. You see the primitives before the cloud wraps them.

🛡️ Session B = Key Management at Scale

A KMS holds master keys in hardware, generates one-time data keys (envelope encryption), and makes deletion provable (cryptographic erasure). Keys live in the KMS, not on disk.

✅ The Rule

Encryption is only as strong as its key management. The algorithm is public, but the key is the real secret. Protect keys, rotate them, and destroy them provably when they're no longer needed.
