Step 0 · Big picture

One cluster, two tenants, three walls

Lab 2 asks: can two customers ("tenants") share one cloud without seeing or hurting each other? The answer is no — not by default. Isolation has to be built, in three dimensions.

The three isolation dimensions
🧱 Compute Who gets the CPU/memory, and who can hog it.
  • 🏠 Namespaces — separate rooms (Task 1)
  • ⚖️ ResourceQuota — spending limits (Task 3)
🕸️ Network Can pods in one room dial pods in another?
  • 🚪 The default-open risk (Task 2)
  • 🧱 NetworkPolicy default-deny (Task 4)
  • 🔬 Egress allow-list (Task 7)
💾 Storage Can tenant A read tenant B's data — even after deletion?
  • 🔐 Secrets locked with RBAC (Task 5)
  • 👻 Data remanence (Task 6)

The lab's rhythm, repeated every time: show the problem → apply the control → re-run the same test to prove the change. Every claim in the report is backed by a before/after comparison.

Before the tasks

Setup — build the cluster and hire the network police

kind's default networking can't enforce NetworkPolicy — the "walls" between rooms. So the lab builds a cluster with the default plugin switched off, then installs Calico, which can.

SThe commands

CommandWhat it does, in easy words
cat <<EOF | kind create cluster
--name ccse-lab2 --config=-		Creates a disposable Kubernetes cluster in Docker. The config file turns off the default networking plugin and sets a private pod network — because the default plugin ignores NetworkPolicy.
kubectl apply -f
https://...calico.yaml		Installs Calico — the network police force that can actually enforce NetworkPolicy rules. Without it, Task 4's wall wouldn't hold.
kubectl -n kube-system rollout status
daemonset/calico-node --timeout=180s		"Wait until every Calico officer is on duty" — blocks until the calico-node agents on all nodes report ready (or gives up after 180s).
Why: the whole lab depends on NetworkPolicy actually working. Calico makes that possible; the rollout status proves it's deployed before anyone builds a wall.
Session A · Task 1

Two tenants, two rooms, one cluster

Each tenant gets its own namespace (a room) and its own web server with a Service (a phone number).

The layout
🏠 Namespace: tenant-a
  • 🌐 Deployment web (nginx)
  • 📞 Service web :80
🏠 Namespace: tenant-b
  • 🌐 Deployment web (nginx)
  • 📞 Service web :80

Two rooms on the same floor. The doors are unlocked — that's the problem Task 2 demonstrates.

1The commands

CommandWhat it does
kubectl create namespace tenant-a
kubectl create namespace tenant-b		Makes two separate rooms for the two tenants on the same cluster. Each room holds its own toys, kept logically apart.
kubectl -n tenant-a create deployment web
--image=nginx		Deploys a web server (nginx) inside tenant-a's room. -n says "which room".
kubectl -n tenant-a expose deployment web
--port=80		Gives the web server a phone number (a Service), so other pods can dial it by name/IP.
kubectl get pods,svc -n tenant-aLists pods and services in tenant-a — checks the pod is Running and the Service got an IP before testing anything.
Mental model: create namespace = open a new room; create deployment = put a worker in it; expose = give the worker a phone number.
Session A · Task 2

The default-open risk — no wall between rooms

Namespaces are labels, not walls. Nothing stops a pod in one room from dialing a pod in another. The probe proves it.

2The commands

CommandWhat it does
kubectl get svc web -n tenant-b
-o jsonpath='{.spec.clusterIP}'; echo		Finds tenant-b's web server phone number (ClusterIP). -o jsonpath = "extract just the IP field"; echo adds a newline.
kubectl -n tenant-a run probe --rm -it
--image=curlimages/curl --restart=Never --
curl -s -m 5 http://<B_IP>
-o /dev/null -w 'HTTP %{http_code}\n'		From inside tenant-a's room, dials tenant-b's web server. --rm = delete the probe pod when done; -it = interactive terminal; --image=curlimages/curl = a tiny container with curl; -m 5 = 5-second timeout; -o /dev/null = throw away the page; -w 'HTTP %{http_code}' = print only the status code.
Result: HTTP 200. Tenant A reached tenant B — a cross-tenant breach waiting to happen. This is the "default-open" problem: isolation is not automatic on shared infrastructure.
Why remember this? Task 4 re-runs this exact command after building a wall. The before/after difference (200 → timeout) is the proof that the control works.
Session A · Task 3

Contain the noisy neighbour — ResourceQuota

Isolation isn't only walls — one greedy tenant could hog all CPU and memory and slow everyone down. The quota sets a spending limit.

3The commands

CommandWhat it does
cat <<EOF | kubectl apply -f -
+ ResourceQuota YAML		Feeds a quota form to the cluster: tenant-a is allowed at most 5 pods, 1 CPU, 512Mi memory — like a spending limit on a shared credit card.
kubectl describe resourcequota
tenant-a-quota -n tenant-a		Shows the quota's limits and current usage — proof the limit is in place and enforced.
Mental model: the quota is a house rule, not a wall. It doesn't stop tenant A from talking to tenant B — it stops tenant A from eating the whole pizza.
Session B · Task 4

Default-deny network isolation — build the wall

A NetworkPolicy with podSelector: {} and no rules means nobody is allowed in. Flip the switch below to see the same probe change.

🧱 NetworkPolicy default-deny-ingress on tenant-b
Before · Task 2 (no policy)
HTTP 200
tenant-a reached tenant-b — default-open 🚨
After · Task 4 (default-deny)
Timeout
traffic blocked — wall holds ✅

4The commands

CommandWhat it does
cat <<EOF | kubectl apply -f -
+ NetworkPolicy YAML		Builds the wall around tenant-b. podSelector: {} = applies to every pod in the room; policyTypes: [Ingress] with no rules = no one is allowed in. Blocked unless a rule explicitly says otherwise.
kubectl -n tenant-a run probe --rm -it
--image=curlimages/curl --restart=Never --
curl -s -m 5 http://<B_IP>
-o /dev/null -w 'HTTP %{http_code}\n'		The exact same probe as Task 2 — same command, same network, different result: timeout instead of HTTP 200.
Why this is the lab's best proof: identical command, only the policy changed. That single controlled difference is what makes the isolation test valid.
Session B · Task 5

Storage isolation — secrets behind RBAC

Secrets are like keys in a drawer. Tenant A's robot identity gets a job description that only opens its own drawer — never the other tenant's.

The RBAC chain (same idea as Lab 1)
🔐 Secret data in tenant-a — value SECRET_A
🤖 ServiceAccount app-a robot identity in tenant-a
➜
📋 Role reader job description: may only get secrets
➜
🔗 RoleBinding rb hires app-a for the job, in tenant-a only

5The commands

CommandWhat it does
kubectl -n tenant-a create secret generic data
--from-literal=value=SECRET_A		Stores a secret (like a password) in tenant-a's room. --from-literal = "here's the value directly".
kubectl -n tenant-b create secret generic data
--from-literal=value=SECRET_B		Same for tenant-b — a different secret.
kubectl -n tenant-a create serviceaccount app-aCreates a robot identity representing tenant-a's application.
kubectl -n tenant-a create role reader
--verb=get --resource=secrets		Writes the job description: may only read (get) secrets — nothing else.
kubectl -n tenant-a create rolebinding rb
--role=reader --serviceaccount=tenant-a:app-a		Hires app-a for that job. A role does nothing until it's bound to an identity.
SA=system:serviceaccount:tenant-a:app-aStores the robot's full address in a variable so the checks below can pretend to be it.
kubectl auth can-i get secrets -n tenant-a
--as=$SA		"Can this robot read secrets in tenant-a?" → yes (explicitly allowed).
kubectl auth can-i get secrets -n tenant-b
--as=$SA		"Can it read secrets in tenant-b?" → no — no permission exists there, even though it's the same cluster.
Takeaway: the robot can open its own drawer, but the other tenant's drawer is locked — storage isolation, proven with the same auth can-i trick from Lab 1.

6The commands

CommandWhat it does
docker run --rm -v ccse-vol:/data alpine sh -c
'echo SENSITIVE-PATIENT-RECORD > /data/phi.txt;
sync; rm /data/phi.txt;
grep -a SENSITIVE /data/* 2>/dev/null;
echo scan-done'		Starts a tiny Linux container, mounts a disk volume (ccse-vol) at /data, then runs a mini-script: write a sensitive file → flush to disk (sync) → delete normally (rm) → scan (grep) to see if the bytes survived. --rm = remove container when done; -v = attach the volume; sh -c '…' = run the quoted script.
docker run --rm -v ccse-vol:/data alpine sh -c
'echo SENSITIVE > /data/phi2.txt; sync;
dd if=/dev/zero of=/data/phi2.txt bs=1k
count=1 conv=notrunc; rm /data/phi2.txt;
echo wiped'		Same idea, but this time overwrite the file with zeros (dd if=/dev/zero) before deleting it — a secure wipe.
Why it matters: the first command proves the deleted secret is still readable (data remanence); the second shows overwriting before delete reduces the risk. Destroying the data's key instead — cryptographic erasure — is the scalable cloud answer.
Extra Task 7 · Micro-segmentation

Egress default-deny — deny out, allow only what's needed

Task 4 blocked traffic into tenant-b. Task 7 blocks traffic out of tenant-a, then re-opens exactly two doors: DNS, and one specific service on one port.

The egress allow-list
📤 tenant-a (all pods) baseline: default-deny-egress — nothing goes out
✅ Two exceptions
  • 🌐 allow-dns-egress → cluster DNS :53
  • 🕸️ allow-tenant-b-web → tenant-b app=web :80 only
🚫 Everything else blocked — internet, other ports, other pods

And because tenant-b has default-deny ingress, a matching allow-tenant-a-to-web rule in tenant-b is the "welcome mat" that lets the allowed traffic arrive. Both sides must agree.

Egress quiz — which traffic is allowed?
✅ Allowed. The allow-dns-egress exception lets pods resolve names — apps need DNS to work.
✅ Allowed. The allow-tenant-b-web rule (out) + allow-tenant-a-to-web rule (in) agree on this exact path. The probe returns HTTP 200.
🚫 Denied. Only TCP port 80 is in the allow rule — SSH is not.
🚫 Denied. No exception covers it. Deny by default, permit only what's explicitly required.

7The commands

CommandWhat it does
kubectl get pods -n tenant-b --show-labelsChecks the web pod's name tags (labels). The app=web label is the address used to allow traffic to exactly this workload.
kubectl get svc web -n tenant-bVerifies the target service exists and exposes port 80.
cat <<EOF | kubectl apply -f -
+ default-deny-egress (in tenant-a)		Blocks all outgoing traffic from tenant-a's pods — the deny-by-default baseline.
cat <<EOF | kubectl apply -f -
+ allow-dns-egress (in tenant-a)		First exception: DNS (UDP/TCP 53) to the cluster's DNS pods in kube-system.
cat <<EOF | kubectl apply -f -
+ allow-tenant-b-web (in tenant-a)		Second exception: outbound traffic only to pods labelled app=web in tenant-b, only on TCP 80.
cat <<EOF | kubectl apply -f -
+ allow-tenant-a-to-web (in tenant-b)		The matching "welcome mat": since tenant-b has default-deny ingress, this rule lets the traffic from tenant-a arrive at the web pod.
kubectl -n tenant-a run probe-allowed --rm -it
--image=curlimages/curl --restart=Never --
curl -s -m 5 http://10.96.207.129
-o /dev/null -w 'HTTP %{http_code}\n'		The test: dial the web service through all the walls. Returns HTTP 200 — the specifically allowed path still works.
kubectl -n tenant-a run dns-test --rm -it
--image=busybox:1.36 --restart=Never --
nslookup kubernetes.default.svc.cluster.local		The DNS test: resolves a service name through the cluster DNS — proves the DNS exception works.
kubectl get networkpolicy -AThe final photo of every policy across all namespaces — the complete micro-segmentation map.
Key principle: the goal is not to block all egress. It's to block egress by default, then explicitly allow only what the workload needs — deny by default, permit by exception.
Cheat sheet

The flags you'll see everywhere

Half of "understanding the command" is understanding the little flags. Here's every one used in Lab 2.

-nnamespace — which Kubernetes room the command applies to
--namegive the cluster/object a nickname to reference later
--config=-read the cluster config from standard input (the heredoc), not a file
--image=which container image to run (nginx, curl, alpine, busybox)
--rmdelete the pod when done — throwaway probe containers
-itinteractive terminal — attach to the running container
--restart=Neverrun the probe once and exit (no auto-restart loop)
--from-literal=supply a value directly on the command line (secrets)
-v ccse-vol:/datamount a volume at a folder inside the container
sh -c '…'run the quoted script inside the container
--as=impersonate an identity for a can-i check
-o jsonpath=extract one field from the output (e.g. just the IP)
-w '…'curl's write-out — print a custom summary (e.g. status code)
-m 5curl timeout — give up after 5 seconds

The whole lab in three lines

One-line takeaway

🧱 Compute isolation

Namespaces put tenants in separate rooms; ResourceQuota stops one tenant hogging the pizza. (Tasks 1 & 3)

🕸️ Network isolation

Rooms are open by default — NetworkPolicy default-deny builds the wall, proven by HTTP 200 → timeout. (Tasks 2, 4 & 7)

💾 Storage isolation

RBAC locks each tenant's secrets to its own room; deletion alone isn't enough — remanence means secure erase (or destroy the key). (Tasks 5 & 6)

The lab's motto: controls should be tested and verified, not assumed to work just because they're configured. Every wall here came with a before/after proof.
